## 问题描述

在护士长端的"资源调度确认"对话框中，护士分配下拉框无任何可选项，导致无法完成排班流程。此问题严重影响了护士长的日常排班工作，使得系统核心功能无法正常使用。

**症状表现**：
- 护士分配下拉框显示"选择护士"占位符
- 点击下拉框后无任何选项
- 房间选择功能正常，仅护士选择功能异常
- 系统配置页面中所有护士状态均为"可用"

**影响范围**：护士长端排班功能完全不可用

**问题报告时间**：2025-11-27

**问题状态**：已修复

## 根本原因分析

### 数据源不匹配

问题的根本原因是**前端代码调用的是已废弃的`getResources()` API，从`resources`表获取数据，而新系统已迁移到独立的`nurses`和`rooms`表**。

**详细分析**：

1. **旧的实现方式**：
   - 前端调用`getResources()` API获取`resources`表的数据
   - `resources`表是旧的通用资源表，包含所有类型的资源
   - 新系统已将资源拆分为独立的`nurses`、`doctors`、`rooms`表
   - `resources`表中没有护士数据，导致下拉框为空

2. **数据流程**：
```
用户打开排班页面
  ↓
loadData() 函数执行
  ↓
调用 getResources() 获取资源
  ↓
❌ resources表为空，返回 []
  ↓
setResources([])
  ↓
过滤护士：nurses = [].filter(r => r.type === 'nurse')
  ↓
结果：nurses = []
  ↓
渲染下拉框：无选项
```

3. **为什么房间选择正常**：
   - 实际上房间选择也有同样的问题
   - 可能是`resources`表中恰好有房间数据
   - 但护士数据确实是空的

## 数据获取逻辑演进

### 从统一资源表到分离专业资源表

系统经历了从使用统一的`resources`表到分离为专业资源表的数据模型演进。

**旧的数据获取逻辑**：
```typescript
// 旧代码：从resources表获取所有资源
const [appointmentsData, schedulesData, resourcesData] = await Promise.all([
  getAppointments({ status: 'pending' }),
  getSchedules({ date: dateStr }),
  getResources(),  // ❌ 获取resources表
]);

setResources(resourcesData);

// 从resources中过滤出护士和房间
const rooms = resources.filter(r => r.type === 'room');
const nurses = resources.filter(r => r.type === 'nurse');  // ❌ resources中没有护士数据
```

**新的数据获取逻辑**：
```typescript
// 新代码：从独立的nurses和rooms表获取数据
const [appointmentsData, schedulesData, nursesData, roomsData] = await Promise.all([
  getAppointments({ status: 'pending' }),
  getSchedules({ date: dateStr }),
  getAvailableNurses(),  // ✅ 获取可用护士
  getAvailableRooms(),   // ✅ 获取可用房间
]);

setNurses(nursesData);
setRooms(roomsData);
// 不需要过滤，直接使用状态中的nurses和rooms
```

**API端点演进**：
- 旧API：`GET /api/resources` - 从`resources`表获取所有资源
- 新API：
  - `GET /api/profiles/nurses/available` - 从`profiles`表获取可用护士
  - `GET /api/resources/rooms/available` - 从`resources`表获取可用房间

## 性能与可维护性优势

### 1. 性能优势

删除运行时过滤逻辑带来了显著的性能优势：

**旧方式**：
```typescript
// 每次渲染都要过滤
const nurses = resources.filter(r => r.type === 'nurse');  // O(n) 时间复杂度
const rooms = resources.filter(r => r.type === 'room');    // O(n) 时间复杂度
```

**新方式**：
```typescript
// 直接使用，无需过滤
const [nurses, setNurses] = useState<Nurse[]>([]);  // O(1) 时间复杂度
const [rooms, setRooms] = useState<Room[]>([]);     // O(1) 时间复杂度
```

**性能优势**：
- **减少计算开销**：避免了每次渲染时的过滤操作
- **降低内存占用**：不需要在内存中存储和过滤大型资源数组
- **提高响应速度**：组件渲染更快，用户体验更流畅

### 2. 可维护性优势

**类型安全**：
- `Nurse`和`Room`有不同的字段，使用独立类型避免了类型错误
- TypeScript编译时就能发现类型不匹配的问题

**代码清晰**：
- 每个资源类型独立管理，代码意图更清晰
- 避免了复杂的运行时过滤逻辑

**易于维护**：
- 每个资源类型的逻辑独立，修改一个不影响另一个
- 添加新资源类型时，只需添加新的状态和API调用

## GanttChart组件Props重构

### Props接口重构过程

GanttChart组件的Props接口经历了从使用通用资源到使用专业资源的重构。

**修改前**：
```typescript
interface GanttChartProps {
  schedules: ScheduleWithDetails[];
  resources: Resource[];  // ❌ 使用Resource类型
  selectedDate: string;
  onScheduleClick?: (schedule: ScheduleWithDetails) => void;
}

export default function GanttChart({ schedules, resources, selectedDate, onScheduleClick }: GanttChartProps) {
  const rooms = resources.filter(r => r.type === 'room');
  const nurses = resources.filter(r => r.type === 'nurse');
  
  // 使用room.category显示房间类型
  <div className="text-xs text-muted-foreground">{room.category}</div>
}
```

**修改后**：
```typescript
interface GanttChartProps {
  schedules: ScheduleWithDetails[];
  nurses: Nurse[];  // ✅ 独立的护士数组
  rooms: Room[];    // ✅ 独立的房间数组
  selectedDate: string;
  onScheduleClick?: (schedule: ScheduleWithDetails) => void;
}

export default function GanttChart({ schedules, nurses, rooms, selectedDate, onScheduleClick }: GanttChartProps) {
  // 添加辅助函数转换房间类型
  const getRoomTypeLabel = (roomType: string) => {
    const labels: Record<string, string> = {
      vip: 'VIP室',
      treatment: '治疗区',
      consultation: '咨询室',
    };
    return labels[roomType] || roomType;
  };
  
  // 使用room.room_type显示房间类型
  <div className="text-xs text-muted-foreground">{getRoomTypeLabel(room.room_type)}</div>
}
```

**重构优势**：
- **类型安全**：避免了类型转换错误
- **性能优化**：避免了运行时过滤
- **代码清晰**：每个资源类型独立管理
- **易于扩展**：添加新资源类型更容易
