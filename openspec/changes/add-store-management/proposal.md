# Change: Add Store Management System

## Why

当前系统缺少门店（店铺）管理功能，所有资源（护士、医生、房间）和业务流程（预约、排班）都在全局范围内管理，没有按门店进行隔离和组织。这导致以下问题：

1. **资源管理混乱**：无法区分不同门店的护士、医生和房间
2. **权限控制不足**：护士长可以看到和管理所有门店的排班，而不是仅限于自己所在门店
3. **业务流程不清晰**：预约时无法指定门店，导致资源分配困难
4. **扩展性受限**：随着门店数量增加，系统无法有效管理多门店场景

需要引入门店管理功能，将资源和业务流程按门店进行组织和隔离，实现多门店场景下的精细化管理。

## What Changes

### 核心变更

1. **新增门店管理模块**
   - 创建门店（Store）实体和数据表
   - 门店基本信息管理（名称、地址、联系方式、状态等）
   - 门店的启用/禁用状态管理

2. **资源与门店关联**
   - 护士（Nurse）关联到门店
   - 医生（Doctor）关联到门店
   - 房间（Room）关联到门店
   - 用户（Profile）关联到门店（特别是护士长）

3. **业务流程调整**
   - 预约创建时必须先选择门店
   - 预约选择门店后，服务项目、医生等选项根据门店过滤
   - 排班页面按门店过滤，护士长只能管理自己门店的排班
   - 护士任务页面按门店过滤

4. **权限控制增强**
   - 护士长只能查看和管理自己所属门店的数据
   - 销售可以为任意门店创建预约
   - 超级管理员可以管理所有门店

5. **钉钉集成调整**
   - 钉钉部门可以映射到门店
   - 同步用户时自动关联到对应门店

### 数据库变更

- **新增表**：`stores` 门店表
- **修改表**：
  - `profiles` 添加 `store_id` 字段
  - `resources` 添加 `store_id` 字段
  - `appointments` 添加 `store_id` 字段
  - `dingtalk_departments` 添加 `store_id` 映射字段

### API 变更

- **新增 API**：
  - `GET /api/stores` - 获取门店列表
  - `POST /api/stores` - 创建门店
  - `PUT /api/stores/:id` - 更新门店
  - `DELETE /api/stores/:id` - 删除门店
  - `GET /api/stores/:id/resources` - 获取门店资源

- **修改 API**：
  - 所有资源查询 API 添加 `store_id` 过滤参数
  - 预约创建 API 要求 `store_id` 参数
  - 排班查询 API 根据用户门店自动过滤

### UI 变更

- **新增页面**：
  - 门店管理页面（管理员）
  - 门店配置对话框

- **修改页面**：
  - 预约创建表单：添加门店选择（第一步）
  - 排班页面：添加门店过滤器（护士长自动过滤到自己门店）
  - 用户管理页面：添加门店字段
  - 资源管理页面：添加门店字段

## Impact

### 影响的功能模块

- **用户管理**：用户需要关联门店
- **资源管理**：护士、医生、房间需要关联门店
- **预约管理**：预约流程需要先选择门店
- **排班管理**：排班需要按门店隔离
- **任务管理**：护士任务需要按门店过滤
- **钉钉集成**：部门映射需要支持门店

### 数据迁移需求

- 需要为现有数据创建默认门店
- 需要将现有用户、资源、预约关联到默认门店
- 需要提供数据迁移脚本

### 向后兼容性

- **BREAKING**：API 接口变更，预约创建必须提供 `store_id`
- **BREAKING**：数据库 schema 变更，需要执行迁移脚本
- 现有前端页面需要适配新的门店选择流程

**后端**：
- `server/src/services/api.js` - 添加门店相关 API

- `src/db/api.ts` - API 客户端调整

### 测试影响

- 需要更新现有测试用例以包含门店信息
- 需要添加门店管理相关测试
- 需要测试多门店场景下的权限隔离

### 部署注意事项

3. 部署后需要验证现有数据的门店关联是否正确
